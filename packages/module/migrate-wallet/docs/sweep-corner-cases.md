# Sweep corner cases

Enumeration of the corner cases the sweep must handle, grounded in the current
implementation (`src/store/side-effects.ts`). Status legend:

- ✅ handled today (D1)
- ⚠️ partially handled / handled with a generic error
- ❌ not handled — D2 work (or a decision needed)

Spec references are to `docs/wallet-migration-requirements.md` (FR/SR/NFR).

| S1  | Registered, zero rewards                                               | ✅     | Proven live. Stake key left registered (no dereg cert). The 2 ADA deposit stays on the source for a later follow-up sweep.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| S2  | Nonzero rewards withdrawal                                             | ✅     | Proven live (tx `0c726657…`, 7.084176 tADA withdrawn with 6 tokens in one tx). Cardano requires the withdrawal to match on-chain rewards **exactly** at submission, rewards accruing between discovery and submit make the tx invalid. Retry re-fetches reward info (self-healing), but the failure still needs a clear message and test.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| S3  | Registered but not delegated                                           | ⚠️     | UTxO-only sweep, key left registered (not delegated, so nothing to withdraw). Needs a test.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| S4  | Multiple reward accounts (multi-stake-key source)                      | ✅     | Golden-tested: a two-reward-account source produces two withdrawals in one tx, and the retained-deposit figure sums one deposit per registered key.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| S5  | Conway per-cert deposit differs from current `stakeKeyDeposit` param   | ⚠️     | Moot for the sweep itself: no deregistration certificate is ever built (FR-5), so this flow never refunds a deposit. Residual: the review/done screens' retained-deposit figure is computed from the CURRENT param, which can misstate a historic cert's actual deposit. `getAccountRegistrations` could supply actuals. Low likelihood.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| S6  | Source is a registered DRep / has governance deposits (FR-10)          | ⚠️     | Handled by **attest-and-refuse** (requirements v4): the review screen collects pool / DRep / governance-proposer declarations and any declaration refuses the migration, telling the user to retire the role and keep their phrase for the deposits. The gate is user-attested, not chain-verified — an under-declaring user proceeds, and the sweep itself is unaffected (governance deposits are separate from the stake deposit, and no deregistration is built).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| S7  | Delegated and mid-epoch: dereg forfeits the current epoch's rewards    | ✅     | Resolved by leaving the key registered: no deregistration, so the pipeline rewards are not forfeited. They stay on the key for the follow-up sweep.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| S8  | **Withdrawing rewards from a never-vote-delegated stake key (Conway)** | ✅     | Handled by refusal: discovery refuses `rewards-not-vote-delegated` for any rewards-bearing key with no vote delegation at all (any DRep passes — sentinel or specific; the Conway rule only requires that a delegation exists, and the ledger removes delegations when a DRep retires, so a retired target reads as undelegated), disclosing the stuck rewards — and eligibility is **re-checked at sweep time**, so an epoch-boundary change between review and sweep refuses rather than submitting a permanently-invalid tx (unit-tested). Lifting the refusal to actually MOVE such rewards is the two-tx shape below. **Found live on preprod.** `ConwayWdrlNotDelegatedToDRep`: a reward account may only withdraw if its stake credential was vote-delegated to a DRep. Any wallet that earned rewards before governance (or never voted) fails this — the common case for migration sources. The ledger check runs against the **pre-certificate** state (deliberately, so unregister+withdraw-all stays valid in one tx — see `validateWithdrawalsDelegated` in cardano-ledger Conway), so a **same-tx vote-delegation cert cannot cure it** (verified live: adding one still failed). The delegation must be on-chain in a **prior** tx. Safe D2 shape: **tx1 = full UTxO sweep + `VoteDelegation(AlwaysAbstain)`** (leaves nothing spendable on the source, so no compromise-race window), then **tx2 = withdraw + deregister**, with tx2's fee paid by a **destination** input (needs mixed source+destination signing — same machinery as W10 redelegation). Detection is free at discovery: `rewardInfo.drepId == null && withdrawableAmount > 0`. For the D1 proof we ran a standalone abstain-delegation tx (`0a52ef6b…`) before the sweep. |

## Chain-state races (NFR-2, SR-8)

| #   | Case                                                                                   | Status | Notes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| --- | -------------------------------------------------------------------------------------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| R1  | Inputs spent between discovery and submit (attacker with same seed, or concurrent use) | ⚠️     | Submit fails → retryable error. A chunked **resume** now re-fetches UTxOs from the provider and intersects with the pinned set, so spent inputs drop out — and if every pinned input is gone with nothing submitted, the sweep refuses rather than reporting success. A **single-tx** retry still replays the pinned plan by design (nothing unreviewed may be swept), so it re-fails cleanly on spent inputs — safe, but the error still reads "sweep failed" rather than naming the race.                                                |
| R2  | Rewards balance changes between discovery and submit                                   | ⚠️     | Same shape as S2; sweep re-fetches reward info at sweep time (good), but between build and submit the epoch boundary can still race.                                                                                                                                                                                                                                                                                                                                                                                                       |
| R3  | User stalls at the signing prompt past the 2h TTL                                      | ✅     | Expired tx rejected on submit → retry rebuilds with a fresh TTL. Needs a test.                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| R4  | Double submission (SR-17)                                                              | ⚠️     | `exhaustMap` prevents concurrent sweeps. On the **chunked** path this is closed: submitted chunk txIds are tracked (`sweepChunkSubmitted`), a resume intersects live UTxOs with the pin, and an empty intersection with every chunk submitted reports success with the last chunk as receipt — no re-submit. The **single-tx** gap remains: a submit that lands on-chain while erroring client-side has no tracked hash, so a retry replays the plan and the node rejects it as spent — confusing "sweep failed" even though it succeeded. |
| R5  | Protocol parameters change between review and sweep                                    | ✅     | Sweep rebuilds from current store state; the review's fee is explicitly an estimate.                                                                                                                                                                                                                                                                                                                                                                                                                                                       |

## Wallet & import

| #   | Case                                                                 | Status | Notes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| --- | -------------------------------------------------------------------- | ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| W1  | User enters the NEW wallet's phrase as the "old" phrase              | ✅     | Detected at phrase entry: `matchLoadedWallet` derives the walletId from the entered words and compares it to the destination created moments earlier. Refused before import, with copy naming the mistake, so the dedupe-and-wait path is not entered from the wizard.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| W2  | Source seed matches an already-loaded wallet                         | ⚠️     | Refused at entry with its own copy, and the dedupe-and-wait hang is gone. FR-9 is descoped (requirements v4), so refusal is the specified behaviour rather than a shortfall. Refusal used to compose with two other decisions into a dead end: only a `sweeping` failure was retryable, and the imported source stays loaded, so the first discovery failure after a successful import left the wizard refusing every re-attempt for that wallet. A discovery failure is now retried in place, so the flow carries its own way forward. **Still open:** a user who closes instead of retrying re-enters to the same refusal, and the escape hatch is removing the source through the general remove-wallet flow, which nothing in the flow mentions. See `docs/audit/domain-2026-08-11.md` finding 1. |
| W3  | Empty source wallet                                                  | ✅     | `nothing-to-sweep` review state; exercised in the UX walk.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| W4  | Address-level discovery gaps within an account                       | ✅     | Source import uses Lace's standard discovery (stake-key gap 5 / payment gap 100 internally). Requirements v4 makes that the specification — FR-3 now inherits the platform's gaps per NFR-4 rather than naming a bespoke address-20 — so this is compliant, not a fidelity gap.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| W5  | 12-word phrases                                                      | ✅     | Accepted as of this change (12/15/24, matching the platform's restore); Byron-era 12-word Daedalus phrases derive different keys — the import path decides, we only validate BIP-39.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| W6  | Byron/legacy addresses in the source                                 | ⚠️     | Discovery is CIP-1852/Shelley only, and the review screen now states it plainly before the sweep (`disclosure.byron`: pre-2020 Byron-era addresses are not moved). Detection remains unbuilt — disclosed, not detected.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| W7  | Script / datum-bearing / collateral UTxOs at source addresses (OQ-C) | ⚠️     | Both sources drop a UTxO whose payment credential is outside the account's discovered set. Only the SCRIPT class reaches the user, as a review-screen count spanning the source and scanned accounts (no ownership claim). Every other dropped class, including an owned address past the payment gap of 100, trades a pre-submit throw for a logged omission.                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| W8  | Multiple accounts in the source wallet (FR-3 account gap of 10)      | ✅     | Discovery scans account indices 1+ (derive xpub under the auth secret, probe the provider) to a gap of 10 consecutive inactive accounts, resolves each active account's UTxOs and addresses, and the sweep spends them all in one tx witnessed per account. Beyond-gap accounts are agreed-empty (D2). Per-account review rows are a later UI addition.                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| W9  | Non-standard derivation: BIP39 passphrase ("25th word") wallets      | ⚠️     | Lace doesn't thread a passphrase through wallet creation yet (a passphrase-protected seed would derive an entirely different, wrong wallet — indistinguishable from W3 to the user). Rather than ship that silent trap, the source-seed screen now asks upfront ("Does this wallet use a BIP39 passphrase?") and refuses with a dedicated error if the user says yes, instead of importing a wrong-looking-empty wallet. D2: real passphrase support — needs `WalletId.deriveFromMnemonic` to become passphrase-aware too, since the same-seed guard's uniqueness assumption currently ignores it (also covers non-CIP-1852 purposes / hand-entered derivation paths).                                                                                                                                |
| W10 | Redelegation continuity for the destination                          | ❌     | The swept funds arrive unstaked and vote-undelegated. Re-registering + delegating the DESTINATION (same SPO, or the D4 DRep nudge) cannot ride in the sweep tx for free — that tx is witnessed by the source wallet, so same-tx certs mean two-wallet signing. Cheaper: a follow-up tx from the destination once the sweep confirms, presented as part of the flow.                                                                                                                                                                                                                                                                                                                                                                                                                                   |

## Suggested test priority (D2 kickoff)

1. **A2, A3, S2, S4** — golden builder tests (`buildSweepTx` with hand-built fixtures: token bundles, ADA-poor, nonzero rewards, multi reward account).
2. **W1** — same-seed detection (cheap, kills the worst UX trap).
3. **R1, R4** — covered on the chunked path (empty-resume trio: none / partial / complete, receipt pinned); the remaining ask is the single-tx landed-but-errored case.
4. **A5, A6** — explicit failure modes for input-less and over-size sweeps.
5. **N1, R3** — guard-rail unit tests. (X1 is done: cancellation classified and tested on both signing paths.)
