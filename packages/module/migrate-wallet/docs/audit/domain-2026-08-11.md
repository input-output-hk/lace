### 1. A failed or abandoned migration cannot be re-attempted

**Impact** 3/4 | **Size** 2/4 | **Status** undocumented-consequence | **Refs** W2, N3, FR-9, NFR-5
**Evidence** `MigrateWalletWizard.tsx:562-566, 837-845` | `slice.ts:49-52` | `en.json:169`

**What the auditor found** -- Three decisions that are each reasonable on their
own compose into a dead end: only a `sweeping` failure is retryable (every
other failed step, including `discovering`, offers Close only), cancelling
never removes the imported source wallet (retention is deliberate, the source
is "not disposable"), and a fresh wizard run refuses a phrase matching any
loaded wallet ("This wallet is already loaded in Lace...", the FR-9
loaded-wallet-as-source path does not exist in D1).

So the first discovery failure after a successful import leaves the wizard
refusing every re-attempt for that wallet at phrase entry. And discovery
failing is not exotic: the 180s timeout covers the imported account's initial
sync plus the account scan plus the reward fetch (which has no `retryBackoff`,
see N3), so the likely victims are exactly the large old wallets this feature
targets. The same trap closes over a review-stage cancel, an abandoned sweep
failure, and the S8 remediation loop: vote-delegate from the source then
migrate again is exactly what the guard refuses. The escape hatch is deleting
the imported source through the general remove-wallet flow, which resets the
guard, but nothing in the flow tells the user this.

**Why it matters** -- No funds are lost, but the flow dead-ends for exactly its
target users (large old wallets most likely to hit the discovery timeout), and
neither the register nor the README records the consequence.

**Verification** -- Verified at `f881de3eb`: retry dispatch exists only for
the `sweeping` failure path (`MigrateWalletWizard.tsx:562-566`); the `slice.ts`
step-machine comment states "Only a `sweeping` failure is retryable; a
failure from any other step falls back to cancel". Cancel retention and the
same-seed guard mechanics confirmed by read.

### 2. README contradicts the code on deregistration, retry re-planning, platform scope and i18n state

**Impact** 2/4 | **Size** 1/4 | **Status** wrong-status | **Refs** FR-5, NFR-3, NFR-5, S7
**Evidence** `README.md:4-11, 95-102` | `build-sweep-tx.ts:23-38` | `lace-mobile/src/app/feature-flags.ts:81`

**What the auditor found** -- Four load-bearing README claims are false against
the code. It says the sweep moves the "reclaimed stake deposit" and adds
"deregistration per reward account": `buildSweepTx` adds no deregistration
certificate, deliberately (S7), and the UI copy correctly says the deposit
stays. It says retry "re-plans from unspent UTxOs": the opposite, the sweep
replays the plan pinned at review and only re-fetches the reward amounts. It
says the flag is registered in `lace-extension` only: `MIGRATE_WALLET` is
registered on mobile too, which resolves seeded discrepancy 2. And it says
es/ja locales are "English placeholders pending proper translation": 141 of
the 142 migrate-wallet keys are translated in both, the one identical key is
the language-neutral "2 {{ticker}}" (translation quality was not reviewed, but
they are not placeholders).

**Why it matters** -- The README is a named audit baseline; the external audit
starts from it. The FR-5 deviation (key left registered) is real and today
only recorded in a code comment and two register rows -- the document that
measures the feature against the spec says it doesn't exist.

**Verification** -- Verified at `f881de3eb`: README lines 4-11 and 95-102
carry all four claims; `feature-flags.ts:81` registers the flag on mobile;
`buildSweepTx` adds no deregistration certificate.

## Open questions

1. **Owned funds past the payment gap: silent omission vs pre-submit throw
   (W7).** An owned UTxO at a payment index past 100 is never derived, lands
   in `franken` at `scan-active-accounts.ts:263`, gets one `logger.warn`, and
   -- unless it is a script UTxO -- reaches no user-facing surface: the review
   totals exclude it silently and the Done screen reports the migration
   complete. Pre-D1, the same UTxO was pinned into the plan and failed the
   build loudly before submit. The register row (W7) records the omission
   honestly but the trade itself was never judged: is a silent success that
   leaves owned funds invisible in both wallets acceptable for D1, or should
   this class fail loud or be disclosed like the script count is? Evidence
   put up: `scan-active-accounts.ts:226-228, 263-278`, W7 row. Would settle
   it: a maintainer/product decision on disclosure for the non-script dropped
   classes. Note the account-level analogue IS disclosed: `DoneSummary.tsx:123`
   consumes `scannedThroughAccountIndex`, so the scanned account range reaches
   the Done screen -- the address-level case has no equivalent.
