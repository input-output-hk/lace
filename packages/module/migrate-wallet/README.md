# @lace-module/migrate-wallet

Deliverable 1 prototype of the wallet-migration flow
(`docs/wallet-migration-requirements.md`): create a fresh destination wallet,
import a source wallet from its recovery phrase, discover its assets, and
sweep everything (UTxOs + tokens, staking rewards) into the destination. The
source stake keys are **left registered** — deregistering mid-epoch would
forfeit that epoch's pipeline rewards — so the 2 ADA deposit stays on the
source, collectable by a later follow-up sweep (FR-5, S7).

Feature-flag gated by `MIGRATE_WALLET`, registered in **both** `lace-extension`
and `lace-mobile` (`feature-flags.ts:81`).

## How it works

The wizard is a state machine in the `migrateWallet` slice:

```
idle → intro → chooseDestination → [connectDevice] → [createDestination]
  → [backupPhrase ⇄ verifyPhrase] → creatingDestination → enterSeed
  → importingSource → discovering → review → sweeping → done
```

Bracketed steps depend on the destination the user picks, so the path is 3-6
steps long. `wizard-progress.ts` derives the same paths to number them for the
user ("Step 3 of 6") and to drive the progress rail — a hardcoded total would
be wrong on four of the five paths. `stepBack` reverses the arrows as far as
`createDestination`; past that a wallet is persisted and there is nothing to
return to, so those screens offer cancel instead.

The `intro` step explains the whole flow up front (what gets created, which
phrase is the new wallet's vs the old one's, what moves, and that DeFi stays
put) before anything is created.

**Why destination-first?** App-lock setup is first-run-only and
installation-wide, so only ONE wallet can go through onboarding's creation
path. Creating the destination (the keeper wallet) first puts the password
ceremony where it belongs and lets the source reuse that app-lock. It also
shrinks the compromise-race window (NFR-2 / OQ-B): the seed is only entered
once everything downstream is ready, so discovery flows straight into
build+submit without an extra staging dwell — though the source is imported and
fully discoverable across the review screen and signing prompt that still sit
between `discoveryCompleted` and submit. (Agreed with Lace maintainers — see
below.)

- **Destination phrase** is generated by the wizard itself
  (`util.generateMnemonicWords`, SR-13) and backed up + re-entered in
  wizard-native steps BEFORE the wallet exists — like the platform's own
  onboarding, and unlike the standalone `RecoveryPhraseVerification` sheet,
  which must decrypt an already-persisted wallet and therefore re-prompts for
  the password mid-wizard. The password and phrase live only in wizard
  component state until handed to `attemptCreateWallet` in one dispatch.
- **Phrase input** is one shared component, `PhraseField`, used by both the
  source-entry and backup-verification steps. Sharing is the point: a hardening
  applied to one field and not the other is the shape a seed bug takes here. It
  sets `autoCorrect={false}` (the `TextInput` atom pins every other autofill and
  spellcheck protection but leaves this one at the platform default, and on iOS
  the keyboard will otherwise rewrite BIP39 words as they are typed), offers a
  Paste control that wipes the clipboard afterwards, and reports a word count
  and the positions of words that are not in the BIP39 wordlist.

  **The verification field never reports which position is wrong.** Filling all
  24 slots with one candidate would test it against every position at once, so
  position-level feedback collapses recovering the phrase from 2048^24 guesses
  to 2048 submissions. The word counter and the wordlist check are safe because
  both are pure functions of the user's own input and a public wordlist; a
  per-position verdict is a function of the secret. Paste is likewise off on
  that field: it exists to prove the user can reproduce the phrase from their
  own backup.

- **Phrase normalisation** lives in `phrase-input.ts`, shared by both steps.
  Beyond trim/collapse/lowercase it strips invisible non-`\s` characters
  (zero-width space, ZWNJ, ZWJ, word joiner, soft hyphen) that survive a paste
  from a PDF or a password manager and otherwise fail validation with an
  unexplained "invalid phrase", and applies NFKD. NFKD is load-bearing, not
  cosmetic: `bip39` normalises internally, so a fullwidth-Latin phrase validates
  while the raw codepoints reach `WalletId.deriveFromMnemonic`, which hashes
  them verbatim — the same seed then yields a different wallet id and
  `matchLoadedWallet` stops recognising an already-loaded wallet. Both
  transforms are monotonic: the English wordlist is pure ASCII, so anything they
  change could not have been a wordlist hit beforehand.
- **Destination creation** goes through `onboardingV2.attemptCreateWallet`
  WITH the pre-verified phrase as the FIRST wallet, which sets up the
  app-lock. Supplying the phrase takes onboarding's recovery path, so the
  wallet is born `isPassphraseConfirmed` — the SR-10 gate is the in-wizard
  verification, structurally unskippable because creation is gated on it.
  (Deviation from SR-10's suggested mechanism, which names the sheet —
  flagged for maintainer review, along with the destination phrase now
  transiting one `attemptCreateWallet` payload like the source phrase.)
- **Source import** goes through `accountManagement.attemptCreateWallet` (with
  the recovery phrase) as a SECOND wallet, which reuses the existing app-lock
  (re-auth, not re-setup). That path emits no `createWalletSuccess`, so the
  source is detected by watching the repo for a new wallet entry.
- **Discovery** (`makeRunDiscovery`) waits for the imported account to sync
  (UTxOs + addresses + protocol params), fetches reward-account info fresh
  from the provider, and dry-builds the sweep tx for a fee estimate (FR-3;
  an unbalanceable dry build surfaces FR-8's hard error).
- **Sweep** (`makeRunSweep`): triggered by the review confirm (`sweepStarted`)
  or a retry, replays the plan pinned at review — spending anything but the
  reviewed set is what the pin prevents. A resume after a partial failure
  re-fetches live UTxOs from the provider and intersects them with the pinned
  set, so already-spent inputs drop out and nothing unreviewed can join;
  reward amounts are re-read fresh either way. Success on an empty
  intersection is claimed only when every planned chunk is on-chain — anything
  short fails rather than reporting funds arrived that did not. Builds with
  `TransactionBuilder` (`addInput` per UTxO, rewards withdrawal only — no
  deregistration certificate — and `setChangeAddress(dest)`); when the signed
  tx would exceed `maxTxSize` the plan splits into sequential chunks signed
  and submitted under a single authentication (FR-6; ADR 57). Signs through
  the standard `SignerFactory` over the imported source wallet, submits, and
  emits a pending activity for the destination account. A dismissed signing
  prompt is a cancellation, not a failure: it returns to review (or to the
  paused screen mid-plan), never to an error offering "Try again" for a plan
  that never started.

## Agreed with Lace maintainers (2026-07-11)

- Destination-first ordering (above) is the intended shape.
- The source is **not** disposable — it's retained for manual cleanup the
  sweep doesn't cover (DeFi, leftovers). The productionised design (D2) imports
  it **hidden**: flagged read-only in wallet metadata, suppressed from wallet
  lists and CIP-30/dApp access (the migration builds its own recovery txs, so
  it never needs CIP-30), associated back to the destination, and able to
  co-exist with a later normal restore of the same seed (which clears the
  hidden flag). D1 imports the source as a plain retained wallet; the
  hidden-metadata / CIP-30-filtering / co-existence layer is D2.

The UI is a global overlay (`loadGlobalOverlays`) so it works from the
onboarding surface (no wallets loaded). Every step renders through a shared
`WizardFrame` (width-constrained card with a step indicator and a NEW/OLD
wallet tag) rather than ui-toolkit `Modal`s, which cap at 33% of the viewport
with no minimum width. During `sweeping` the wizard renders a full
progress card (the floating banner it once collapsed into read as the app
moving on while funds were in flight). The wallet-import
flow ends in its own "All done" sheet — redundant mid-wizard, so the wizard
closes sheets as it advances (backed by the sheet-dismissal watchdog in
`@lace-lib/navigation`, which force-removes routes when the TrueSheet
dismissal cascade stalls on web).

## Deliberately out of prototype scope (D2 work)

- "Add wallet" entry point. Loaded-wallet-as-source (FR-9) is **descoped**
  (requirements v4): a loaded wallet is refused at phrase entry, and the
  workaround is to remove it from Lace first. The dead end this once created
  (`docs/audit/domain-2026-08-11.md` finding 1) is closed: a failed discovery
  now retries in place (`discoveryRetryRequested`), so the flow carries its
  own way forward.
- Chain-side verification of FR-10's roles. The shipped gate is
  **attest-and-refuse** (requirements v4): the review screen collects the
  pool / DRep / governance-proposer declarations and any declaration refuses
  the migration. Verifying those roles against the chain stays out of scope.
- Persisted/resumable wizard state across restarts (NFR-5) — the sweep retry
  resumes the pinned plan, but the wizard itself resets on app restart.
- Full Appendix-C test depth. Initial unit tests exist (`test/store/`): the
  slice state machine, `buildSweepTx` golden tests against the real
  `TransactionBuilder`, and marble tests for the backup gate and sweep
  orchestration. `docs/sweep-corner-cases.md` enumerates the remaining
  corner cases with a suggested priority order.
- SR-2 tension: like the standard onboarding flow, the recovery phrase
  transits `attemptCreateWallet`'s action payload. The spec wants this
  minimized for the migration flow specifically — revisit in D2.
- Password UX: collected once in the wizard and reused for both wallets;
  strength rules are minimal (length ≥ 8).
- i18n: es/ja carry values for every migrate-wallet key; the only values
  identical across locales are language-neutral (the `{{amount}}`
  placeholder and the `、`/`, ` list separator). Translation quality has not
  been reviewed — provenance records the technique per key, and the
  namespace is machine-translated pending native review.
